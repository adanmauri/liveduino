# Rules: library guardrails

Liveduino exists so an Arduino user can drive a board from Python with zero learning curve. These
constraints protect that promise and the hardware it talks to.

## Arduino API fidelity: [ADR-0007](../../docs/adr/0007-the-public-api-mirrors-arduino-wiring.md)

- Public board methods use **camelCase** to match Arduino/Wiring: `pinMode`, `digitalWrite`,
  `digitalRead`, `analogRead`, `analogWrite`, `tone`, `noTone`, `pulseIn`, `shiftOut`, `shiftIn`.
  Same names, same semantics, same argument order.
- Constants mirror Arduino (`INPUT`, `OUTPUT`, `INPUT_PULLUP`, `HIGH`, `LOW`, `LSBFIRST`,
  `MSBFIRST`, analog pins `A0`-`A20`), typed through the `PinMode`, `DigitalValue` and `BitOrder`
  `Literal` aliases.
- Host-side timing (`delay`, `delayMicroseconds`, `millis`, `micros`) are **`Board` methods** that
  run on the host ([ADR-0010](../../docs/adr/0010-timing-runs-on-the-host.md)); `millis` and
  `micros` count from the moment the board connection was created. The pure value helpers
  `map_range` and `constrain` are module-level functions.
- Operations the active protocol cannot perform (`tone`, `noTone`, `pulseIn`, `shiftOut`,
  `shiftIn` over StandardFirmata) keep their Arduino signatures and raise
  `UnsupportedOperationError` until a protocol supports them
  ([ADR-0011](../../docs/adr/0011-unsupported-operations-keep-their-arduino-signature-and-raise.md)).
- No breaking changes to the public API: it is published on PyPI.

## Layers: [ADR-0008](../../docs/adr/0008-board-protocol-and-driver-are-separate-layers.md)

- User API → `Board` subclass → `ProtocolClient` → `Driver` → firmware. Never short-circuit a
  layer.
- Never expose protocol internals (Firmata bytes) or driver internals through public exports.
- The Firmata 2.x wire protocol is implemented in-house (`FirmataProtocol`) over a `Driver`; do not
  add a third-party Firmata library
  ([ADR-0009](../../docs/adr/0009-firmata-is-implemented-in-house-over-standardfirmata.md)). The
  TCP and Bluetooth drivers use the standard library.

## Board catalog: [ADR-0012](../../docs/adr/0012-boards-are-auto-discovered-and-the-firmware-overrides-the-catalog.md)

- `Board` (`boards/board.py`) is the base class: the Arduino API plus the pin map, capabilities and
  `connect`.
- Each concrete board is a `Board` subclass in its own file under `src/liveduino/boards/catalog/`
  (for example `catalog/arduino_uno.py` defines `ArduinoUno`). Subclasses set class attributes
  (`id`, `name`, `digital_pins`, `analog_pins`, `pwm_pins`, ...) and may add board-specific
  behavior.
- The registry (`boards/registry.py`) **auto-discovers** every subclass: a new file is enough to
  register it for `connect("<id>", port)` and `available_boards()`. Nothing else needs editing.
- `boards/catalog/` holds board definitions only.

## Errors

- Raise the specific `liveduino.exceptions` type (`LiveduinoError` and its subclasses) with a
  descriptive English message.
- Validate pins, modes and values at the `Board` layer, before anything is sent to the device:
  `InvalidPinError`, `InvalidModeError`, `InvalidValueError`.
- `UnsupportedOperationError` when the active protocol cannot perform an Arduino operation;
  `NotImplementedError` for abstract methods and unimplemented protocols.

## Hardware

- The serial port and the connected board are shared, stateful resources: always close
  connections cleanly.
- Unit tests never assume a board is present; hardware access belongs to integration tests
  (`LIVEDUINO_PORT`).
- Flashing overwrites the board's firmware. The flashing integration test runs only with its own
  variable (`LIVEDUINO_FLASH_PORT`); never set it without the user's go-ahead.

## Bundled firmware: [ADR-0014](../../docs/adr/0014-firmware-is-bundled-and-flashed-in-pure-python.md)

- The images under `src/liveduino/firmware/` are generated by `make firmware`
  (`scripts/build_firmware.py`), never written by hand.
- They are a **CI/Linux artifact**: `avr-gcc` differs between macOS and Linux, so a local macOS
  build does not match what CI verifies. NEVER commit locally built firmware; regenerate it with
  the Firmware workflow (`make actions workflow-firmware`).
- The pinned Arduino core and library versions live in the `Makefile` and are shared with CI.
